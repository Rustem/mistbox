Oncall Playbook

How to read the logs when a customer says something didn't happen (an email, a status update) — and what a normal line looks like versus a broken one.

1Connect and read the logs

SSH in with vmssh, then filter the storefront logs down to just this app's own lines — everything real is tagged [mistbox].

vmssh deploy 'cd ~/code/mistbox && docker compose -f docker-compose.yml -f docker-compose.qa.yml logs storefront --since 24h | grep "mistbox\]"'

2What to look for

Every line names what happened in plain words. A normal line says something was sent or created. A broken one is shouting in CAPS and says what FAILED or was NOT SENT or rejected — and the reason is usually right there in the same line, no further digging needed.

3Two real examples

broken
[mistbox] saleor webhook rejected: bad or missing secret

Saleor tried to tell us a box shipped, and we refused to listen. This is what caused the missed shipped-email — the secret we check against didn't match what's in 1Password. Fix: delete and recreate the webhook with the current secret.

not actually broken
[mistbox] SHIPPO REGISTRATION FAILED for order 1 (933...): not a valid test tracking number

Looks alarming (all caps, "FAILED") but on qa this is expected — the Shippo API key here is test-mode and only accepts Shippo's own sample tracking numbers, not real ones. Nothing to fix.

normal
[mistbox] shipped email for order 1 sent (01a0c216-e77e-75ac-8327-bc0cc2099bd1)

Success. The id at the end is Resend's own message id — paste it into Resend's dashboard to see delivery status for that exact email.
