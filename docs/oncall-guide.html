For a report shaped like "a customer says X didn't happen" or "the site/dashboard is behaving wrong." This is triage, not infrastructure — for restarting services, reading resource usage, or SSH access, see the separate QA Operations reference. Every command and log line below is real, pulled from this codebase — not generic advice.

The shape of every incident here

Saleor / Stripe / Shippo event → one webhook route → several independent side effects

Every customer-facing effect — an order confirmation, a shipped notice, a delivery alert — is triggered by an external event landing on one of three routes (stripe/webhook, saleor/webhook, shippo/webhook), each of which fans out to a handful of independent, failure-isolated side effects: a metadata write, an external API call, an email send. One failing never silently blocks the others, and — this is the important part — every one of them logs its own outcome, with a specific reason, not a generic error. That's what makes this class of bug fast to diagnose: you are almost never guessing, you're reading.

01

Start here, every time

Before jumping to a specific symptom below, run these three in order. Most reports resolve at step 2.

1

Name the event that should have fired. "Customer didn't get an email" isn't specific enough — which email? A confirmation comes from a Stripe checkout session completing; a shipped notice from a Saleor fulfillment tracking number; a delivered notice from a Shippo carrier status. Each is a different route, different log lines, different failure modes. If you can't name which one, ask what the admin actually did (or check the order's own history — step 3) before searching logs blind.

2

Grep the storefront logs for mistbox\]. This tag marks every line this app itself writes — filtering to it removes all Next.js/Docker noise and leaves only the lines that explain what happened.

vmssh deploy 'cd ~/code/mistbox && docker compose -f docker-compose.yml -f docker-compose.qa.yml logs storefront --since 24h | grep "mistbox\]"'

Read the log reference table below — most lines name the exact cause in the message itself.

3

Check the order's own state against Saleor's. mistbox_stage and mistbox_history in order metadata are this app's record of how far processing actually got — compare against what Saleor's native fields show (a fulfillment exists, a tracking number is set). A mismatch — Saleor looks done, our stage is one step behind — tells you precisely which side effect never completed.

{ orders(first: 1, channel: "mistbox-us", filter: { search: "<order number>" }) {
  edges { node { number userEmail metadata { key value }
    fulfillments { trackingNumber status } } } }
}
02

Log line reference

Every [mistbox] line this codebase can emit around an order, grouped by the route that writes it. Search this table for a fragment of what you saw in the logs.

stripe/webhook — checkout → order created → confirmation email

Log fragmentMeaning
order N created from Stripe session ... Normal. The order exists in Saleor now.
confirmation for order N sent to ... (id) Normal — success. The (id) is the Resend message id, useful for looking it up in Resend's own dashboard.
CONFIRMATION NOT SENT for order N to ... Order was created fine; the email itself failed (Resend outage, bad API key, address rejected). The order is real and paid for — this is purely a notification miss.
order N has no address, skipping confirmation Expected for a checkout with no shipping address collected — not a bug by itself.
PAID BUT NOT ORDERED — session ... Worst case: Stripe has the customer's money and Saleor has no order. Escalate immediately — see Escalate.
webhook signature check failed STRIPE_WEBHOOK_SECRET mismatch between Stripe's dashboard and this environment's 1Password value — same class of bug as the Saleor webhook secret issue below.
checkout already completed / payment already recorded — skipping Normal. Stripe redelivers events; these guards are why a customer never gets charged or emailed twice.

saleor/webhook — tracking added → stage advance, Shippo registration, shipped email

Log fragmentMeaning
saleor webhook rejected: bad or missing secret The exact bug from Sept 2026. Saleor sent the event; this route's shared-secret check failed. See webhook secret drift below.
saleor webhook: order not found The event referenced an order id this environment doesn't have — almost always a webhook still pointed at the wrong environment (dev event hitting qa, or vice versa).
SHIPPO REGISTRATION FAILED for order N (...) Stage still advances and the email still sends regardless — this is deliberately non-blocking. On qa specifically, check whether the tracking number is one of Shippo's real sandbox test numbers; a real-looking number in test mode always fails this exact way and is not a bug.
shipped email for order N sent (id) Normal — success.
SHIPPED EMAIL NOT SENT for order N Stage and tracking are correct in Saleor; only the notification failed. Safe to fix the cause and manually replay (see the symptom card below).

shippo/webhook — carrier status change → delivered email / delivery problem

Log fragmentMeaning
shippo webhook rejected: bad or missing token Same class as the Saleor secret issue, different shared value (SHIPPO_WEBHOOK_TOKEN, passed as a query param at registration, not a header).
shippo webhook without order metadata or status A tracking event arrived for a number Shippo knows about but this app can't map back to an order — check the number was registered correctly in the first place.
DELIVERY PROBLEM on order N: status Not a bug — a real carrier exception (returned, damaged, address issue) being surfaced. Worth a human look at the actual order.
delivered email for order N sent (id) Normal — success.
DELIVERED EMAIL NOT SENT for order N Same shape as the shipped-email miss — carrier state is correct, only the notification failed.

Admin-facing (label purchase, login, newsletter, customer sync)

Log fragmentMeaning
label email for order N sent (id) This is the admin's own label-purchase confirmation — a different email from the customer's "shipped" notice. Don't confuse the two when triaging "no email" reports.
LABEL BOUGHT BUT ORDER N NOT FULFILLED Money was spent on a real shipping label with Shippo, but Saleor's fulfillment record wasn't created. The label/tracking number in the log line is real — go create the fulfillment by hand rather than buying a second label.
customer sync failed for ... : ... MANAGE_USERS The app token lacks a permission it needs for this one, non-critical step (creating a Saleor customer record for marketing/history). The order itself is unaffected — cosmetic unless someone's specifically relying on customer records existing.
admin login / forgot / reset: Saleor unreachable The api service is down or unreachable from the storefront container — check docker compose ps and the Docker-networking root cause below before assuming it's a code bug.
03

By symptom

Deeper walkthroughs for the reports that come up in practice.

Customer says they got no email Customer got the same email twice Order looks stuck / tracking not updating Images broken on the storefront Site or dashboard unreachable (502) Customer was charged, no order exists

Customer says they got no email most common

First, name which email. Confirmation (checkout), shipped (tracking added), delivered (carrier confirms delivery), or the admin's own label-purchase receipt — each is a different route (see the log reference) and the fix differs.

  • Grep for that order's number in the storefront logs. A "... NOT SENT" line names the real reason — usually Resend being unreachable, or a webhook rejected upstream so the send never happened at all.
  • If nothing at all was logged for that order around the expected time, the triggering webhook likely never arrived — check it's registered and active (webhook secret drift is the most common cause on this project so far).
  • Check the order's mistbox_stage. If it's one step behind what the dashboard shows, the webhook fired but a side effect (including the email) didn't complete — see step 3 of Start here.

Fix: once the root cause (usually a stale secret) is corrected, replay the missed event by hand rather than asking the admin to redo the original action:

curl -X POST "https://api.qa.mist.box/api/saleor/webhook" \
  -H "Content-Type: application/json" \
  -H "X-Mistbox-Webhook-Secret: $(op read op://Mistbox/mistbox-qa/SALEOR_WEBHOOK_SECRET)" \
  -d '{"fulfillment":{"id":"","trackingNumber":""},
       "order":{"id":"","number":""}}'

Swap the URL/header for shippo/webhook or stripe/webhook if that's the missing one instead — check that route's own secret-check code for its exact header/param name first.

Customer got the same email twice

Every one of these three webhooks can be redelivered by its sender (Stripe, Saleor, Shippo all retry on a non-2xx or a timeout) — duplicates are expected traffic, not a bug by default. What matters is whether the idempotency guard for that specific side effect held:

  • Confirmation email: guarded by "checkout already completed" / "payment already recorded" checks before the order is even created.
  • Shipped email + Shippo registration: guarded by the shippo_track_registered metadata flag matching the tracking number — if this flag is missing or wasn't written (e.g. from a crash between sending the email and saving the flag), a redelivery will resend.

If a genuine duplicate happened: check whether the corresponding metadata flag is actually set on the order now. If not, the guard has a real gap worth fixing in code — this is a bug report, not a one-off to patch by hand.

Shippo registration specifically is not idempotent — registering the same tracking number twice sends the customer duplicate carrier-status emails for the rest of that shipment, permanently, with no way to undo it. If you suspect a double-registration happened, that's worth flagging even if nothing looks broken yet.

Order looks stuck / tracking isn't updating

The visible timeline (confirmed → packing → card_written → sealed → shipped → in_transit → delivered) is a mix: the first four are advanced by Daniya by hand in the dashboard, the last three come from carrier data via the Shippo webhook.

  • Stuck before "shipped": this is a manual stage — nothing automated should have moved it. Check with Daniya whether she actually advanced it; this usually isn't a system bug at all.
  • Stuck at "shipped", never reaches "in_transit"/"delivered": means Shippo tracking was never successfully registered for this order — check for a SHIPPO REGISTRATION FAILED line around when it shipped. If the tracking number is a real carrier number and this is qa (test API key), this is expected — Shippo's test mode only tracks its own sample numbers, not real ones.

Images broken on the storefront (box art, item photos)

Historically caused by two separate, now-fixed infrastructure bugs — worth checking both still hold before assuming a new cause:

  • Django's Sites-framework domain reverting to localhost:8000 (e.g. after a database restore) — see ops/set-site-domain.sh.
  • Caddy's /media/* static-file block missing after a Caddyfile change — self-hosted Saleor never serves media itself once DEBUG=False.

Quick check: curl -o /dev/null -w '%{http_code}\n' <any image URL from the page> — a 404 with the URL still containing localhost:8000 means the first cause; a 404 with the right domain means the second.

Site or dashboard unreachable (502/504)

docker compose ps saying every container is healthy does not prove Caddy can actually reach it — hit the real domains directly:

curl -s -o /dev/null -w "storefront %{http_code}\n" https://qa.mist.box/
curl -s -o /dev/null -w "dashboard  %{http_code}\n" https://admin.qa.mist.box/
curl -s -X POST https://api.qa.mist.box/graphql/ -H 'Content-Type: application/json' -d '{"query":"{shop{name}}"}'

A 502 specifically on one service almost always means that service has no explicit networks: entry in its compose definition and landed on Docker's default network instead of saleor-backend-tier — confirm with docker inspect <container> --format '{{.NetworkSettings.Networks}}' and compare against Caddy's own.

Customer was charged but no order exists urgent

Look for PAID BUT NOT ORDERED in the logs — the log line includes the Stripe session id and email, both needed to manually reconcile. This means Stripe successfully charged the card but something threw while creating the Saleor order from that session.

This is the one case in this guide where "let it resolve itself" is wrong. Stripe will not retry a completed checkout session. Pull the session from Stripe's dashboard by id, read the storefront logs around that timestamp for the actual exception, and either replay the order-creation logic manually or refund — don't leave a charged customer without a box or a refund while investigating.
04

Root causes seen more than once

Webhook secret drift seen: Sept 2026

Saleor, Stripe and Shippo webhooks are each authenticated with a shared secret set at registration time — none of them let you read that secret back out afterward to compare it against 1Password. If the value in 1Password is ever rotated, or a registration script used a different source than the environment's own secret, the two silently disagree forever, with zero symptoms until an event actually arrives and gets rejected.

Fix: delete and recreate the webhook with the current 1Password value — there is no way to patch just the secret. For the Saleor one specifically, query { app { webhooks { id name targetUrl isActive } } } (the app token's own app field — the top-level webhooks query silently returns empty for an app token instead of erroring), delete the match, recreate with customHeaders: {"X-Mistbox-Webhook-Secret": "<current secret>"}.

Site-framework domain default

Every fresh Saleor install defaults Django's Sites-framework domain to localhost:8000, and nothing in a normal deploy touches it. Every absolute media/thumbnail URL Saleor builds uses this value — wrong on any real environment, but easy to miss because it can coincidentally still resolve to something on whoever's own machine happens to have a service on port 8000.

Docker networking gaps

A service with no explicit networks: key lands on Compose's default network, invisible to anything explicitly on saleor-backend-tier. Reads as a 502 with every container reporting healthy.

SSH agent key pileup

An agent holding several keys can exhaust the server's MaxAuthTries before ever offering the correct one — "Permission denied (publickey)" even though the right key is loaded. Use vmssh (ops/vmssh), which sidesteps this by fetching the key fresh and connecting with -o IdentitiesOnly=yes.

05

When to stop and escalate

This guide covers triage a solo oncall can run alone. Stop and bring in Rustem directly rather than continuing to dig when:

  • A customer was charged and has no order (see above) — money is real, time matters.
  • A fix would require rotating a secret used by more than one integration (the Saleor webhook secret is also read by other things — check env/saleor.env.tpl before rotating anything, not just deleting/recreating one webhook).
  • You're about to run anything destructive — docker compose down -v, a database restore, deleting a Saleor object — to fix a symptom rather than reading logs further. Restoring a snapshot is the last resort in the QA Operations guide, not a first troubleshooting step.
  • The same symptom recurs after a fix that should have been permanent — that usually means the root cause wasn't what was fixed.
